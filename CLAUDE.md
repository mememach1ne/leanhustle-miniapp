# LeanHustle Miniapp

Telegram Mini App **и** браузерное веб-приложение для реселл-бизнеса (товары Poizon/Dewu, Китай→Россия) + Telegram-бот @lh_poizonbot. pnpm/tsx-монорепо. Отдельный сервис цен живёт в проекте **dewu-api** (см. «Движок цен»). Доставка Китай→РФ — через форвардера **RAKETA** (my.raketacn.ru), см. «RAKETA».

## Структура
- `apps/web` — Next.js 15, фронт (UI Telegram Mini App и браузерной версии)
- `apps/api` — NestJS-бэкенд (products, catalog, cart, orders, pricing, crypto-payments, delivery-addresses, raketa, loyalty, admin, auth)
- `apps/bot` — Telegram-бот (клиентское меню + панель менеджера)
- `packages/shared` — общие TS-интерфейсы/enum'ы (api и bot берут **собранный `dist`**, web — исходники)

Git: `github.com/mememach1ne/leanhustle-miniapp`, ветка `master`. Коммить и пушить в master без вопросов (см. память).

## Домены / поверхности (всё — один и тот же код)
- **Telegram Mini App** → `apps/web` (бот: кнопка «Открыть MiniApp» → `https://leanhustle.ru`).

- Не относится к проекту: `leanhustle.net` — статический сайт владельца (`/var/www/leanhustle.net`); `work.leanhustle.net` — `lh-workbot`.

## Ключевые подсистемы
- **Авторизация:** Mini App — Telegram `initData`. Сайт — вход через бота: `POST /auth/bot-login/start` → ссылка `t.me/lh_poizonbot?start=login_<code>` → бот (подписка на @lh_poizon + кнопка «Да, это я») → `/auth/bot-login/confirm` (internal token) → сайт поллит статус. Код в `auth/services/bot-login.service.ts`.
- **Цены:** `pricing.service.ts`. Комиссия из настроек минус скидка лояльности (или ручная `commissionOverride`). **Доставка — таблица «категория × размер»** `pricing/data/delivery-price-table(.data).ts` (цены из калькулятора RAKETA до Москвы) + **региональная поправка**: регион адреса → ближайший из 16 миллионников (`pricing/data/delivery-hubs.ts`, без адреса — Москва); цена СДЭК «Стандарт» до ПВЗ миллионника берётся из публичного калькулятора для 4 эталонных посылок раз в 30 дней (`delivery_city_rates`) и интерполируется (`services/regional-delivery.service.ts`). Применяется при оформлении, в корзине (`GET /cart/delivery-estimate?addressId`) и в ручном заказе с ПВЗ. Неизвестные категории молча пишутся в `delivery_category_weights` (уведомлений нет). Дозаполнение — по памяти `delivery-price-table`, скрипт `src/scripts/unfilled-delivery-categories.ts`.
- **Оплата:** USDT через Bybit V5 (`crypto-payments`), матчинг по уникальной сумме; ETA зачисления по сетям — `PAYMENT_NETWORK_ETA` в shared.
- **Оплата через кошельки Telegram:** CryptoBot (Crypto Pay API, `pay.crypt.bot`) и xRocket (**новый** Pay API `https://pay.api.xrocket.exchange`, `Authorization: Bearer`, `/api/v1/invoices`; старый Rocket Pay `pay.xrocket.tg` — legacy, ключи нового бота к нему не подходят) — `crypto-payments/services/wallet-pay.service.ts`. Счёт в USDT = сумма заказа + комиссия платёжки (настройки `cryptoBotFeePercent`/`xRocketFeePercent`, платит клиент, это написано при выборе). Деньги сразу на балансе приложения в боте. Проверка оплаты — опрос каждые 20 с → `PAID_AWAITING_PURCHASE`, `paidVia CRYPTOBOT|XROCKET`. Токены `CRYPTOBOT_API_TOKEN`, `XROCKET_API_TOKEN` в `apps/api/.env` (без токена способ скрыт). Звёзды Telegram не подключали: вывод только через 21 день.
- **Реферальная программа** (`modules/partners`, внутри «Лояльности»): ссылка `t.me/lh_poizonbot?start=ref_<code>` (`users.referral_code`), привязка только НОВОГО пользователя навсегда (`users.referred_by_id`, бот → `POST /referrals-internal/attach`). Реферал получает `referralPercent`% от **нашей комиссии** с каждого заказа (`referral_rewards`: PENDING → AVAILABLE после доставки → PAID). Вывод — заявкой через менеджера от `referralMinPayoutUsd`, отмечается в админке → «Прибыль».
- **Прибыль партнёров:** `partners/ledger.service.ts` (cron 5 мин) делит комиссию каждого оплаченного заказа (формула как в отчёте: original×c/(100+c) − скидка) минус реф-бонус между партнёрами по долям (`staff_accounts.profit_share_percent`, доли задаёт владелец `is_owner` — @zanyatij), записи `profit_entries`; отмена заказа → REVERSAL. Пока долей нет — заказы ждут. Вкладка админки «Прибыль»: баланс, история, адрес вывода, доли (владелец), заявки рефералов. Вывод USDT через Bybit (`profit_withdrawals`) отдельным ключом `BYBIT_WITHDRAW_API_KEY/_SECRET` — по кнопке и 1-го числа (10:00) автоматически; смена адреса → уведомление партнёрам и блок вывода на 24 ч. Заказы, оплаченные до запуска (2026-10-07), помечены учтёнными.
- **Адреса доставки:** клиент выбирает **город → способ получения → пункт/дверь** из справочника RAKETA (`web/components/ui/pickup-point-picker.tsx`; `GET /delivery-points/cities|options|points?carrier=|streets`): пункт СДЭК, отделение Почты России, «пункт выдачи партнёра» (свои ПВЗ RAKETA, только Дальний Восток — Хабаровск, Уссурийск; бренд клиенту не показываем) или курьер (улица+дом из подсказок RAKETA `/get_address`, индекс; кв./подъезд/этаж/домофон или «частный дом»). Адрес: `carrier` (cdek|pochta|raketa), `kind` (pvz|courier), `courier` JSONB, `pvz_index` = индекс дома для курьера. Старые текстовые адреса помечены «выберите пункт из списка».
- **Способ доставки и срок** (выбирается в корзине): `GET /cart/delivery-estimate?addressId&option` → варианты «перевозчик × ПВЗ/курьер × тариф» (STND Стандарт, EXPR Экспресс, ECON Эконом у партнёра; Тяжеловес не предлагаем; Экспресс, который не быстрее Стандарта, скрыт) с ценой корзины и сроком «дн. от склада в Китае». Цены — `RegionalDeliveryService.optionsFor`: калькулятор RAKETA по городу (все перевозчики × 4 эталонные посылки, кэш 30 дней в `delivery_city_rates` формата `{v:2, options}`, первый запрос по городу ≈7 с, прогрев при сохранении адреса); уровень цены — миллионник региона, если там есть такой вариант, иначе сам город; срок и доступность — сам город; курьер — только перевозчики, чей курьер возит по индексу (`/kd_list`). Таблица = Москва СДЭК ПВЗ Стандарт, сдвиг на разницу участка по РФ. Заказ хранит `delivery_carrier/kind/tariff/courier/days_min/days_max`. Ручной заказ / выбор ПВЗ в админке — перевозчик из точки, скорость стандартная.
- **Доп. услуги RAKETA** (по себестоимости, оплачиваются в счёте доставки RAKETA): упаковка `orders.packaging` box (коробка 150 ₽) | crate (обрешётка 200 ₽) — на **каждый заказ RAKETA** (китайскую посылку); фотоотчёт на вещь `order_items.photo_report` basic (150 ₽) | individual (250 ₽, `photo_report_comment` «что снять»). Уходят в RAKETA при регистрации трека (`packagingService/photoReportService` из `/get_additional_service_list`); если привязан готовый заказ RAKETA — владельцу сообщение «добавьте услуги вручную». PUT заказа RAKETA сохраняет услуги вещей (раньше стирал). `RaketaPhotoReportService` (каждые 20 мин) берёт фото из карточки (`items[].additional_services[].items` — URL), пишет в `photo_report_urls`, шлёт клиенту альбомом в бота (если Telegram не скачает URL — сервер загрузит сам) и показывает на странице заказа; скрытым заказам не шлёт.
- **Страховка RAKETA** («Защита от рисков», 1% от товаров в ₽, платится с доставкой): галочка в корзине и при ручном заказе → `orders.insurance/insurance_rub`, уходит в RAKETA (`insurance: true`).
- **Уведомления клиенту** по статусам: `orders/services/order-notifications.service.ts` (HTML, без эмодзи, кнопки «Открыть заказ/Оплатить», «Менеджер», «Отследить в СДЭК»; `notifyUserText` — произвольный текст клиенту).
- **Кому какие уведомления** (память `feedback-notification-routing`): менеджеру (`MANAGER_TELEGRAM_IDS`) — только работа с клиентами (новые заявки, автооплаты, отмены, помощь с расчётом, выводы рефералов). События RAKETA: плановые → клиенту заказа, требующие действия (ошибки, карантин, непонятные пополнения, объединения/заказы без клиента) → владельцу (`staff_accounts.is_owner`, `RaketaGuardService.notifyOwner`).
- **Клиентская страница заказа:** единый блок «Статус заказа» (`web/components/ui/order-progress.tsx`: этапы заказа + этапы посылки, трек СДЭК с логотипом, «Подробнее о перемещении»), блок «Оплата доставки» с состоянием «Ожидаем оплату…» (повторное нажатие открывает ссылку, страница обновляется сама). Все статусы — по-русски (`web/lib/order-status.ts`).
- **Админка заказа:** выбор ПВЗ СДЭК для старых текстовых адресов (`POST /admin/orders/:id/pickup-point`, пишет в заказ и в адрес клиента); «Скрыть от клиента / Показать клиенту» (`orders.hidden_from_client`, `POST /admin/orders/:id/client-visibility`); кнопки «тот же трек …» в панели RAKETA.
- **«Новый заказ» (`/admin/orders/new`):** ручной ввод товара, если движок не нашёл ссылку (`dwSpuId 'manual'`); черновик всей формы в localStorage на 24 ч (переживает обновление/выкатку, чистится после создания); китайский трек хранится у своей вещи, треки регистрируются в RAKETA **в фоне** (`registerStoredTracks`), ответ создания — сразу.
- **Секреты через скрипт:** `ssh -t root@<server> bash /opt/app/scripts/set-env-secret.sh <KEY>` — скрытый ввод значения в `apps/api/.env` + рестарт api (ключи: CRYPTOBOT_API_TOKEN, XROCKET_API_TOKEN, BYBIT_WITHDRAW_API_KEY/_SECRET). Смена токена движка — `scripts/rotate-engine-token.sh`.

## RAKETA (форвардер) — автоматизация
- Клиент API кабинета: `apps/api/src/modules/raketa/raketa-client.service.ts` (вход `RAKETA_EMAIL/RAKETA_PASSWORD` из `apps/api/.env`, Bearer в памяти, повторный вход на 401). Неофициальный API — эндпоинты взяты из бандла кабинета; официальный только по договорённости.
- Логика: `apps/api/src/modules/orders/services/raketa-fulfillment.service.ts`:
  1. Китайский трек на вещь (бот «Китайский трек → RAKETA» / админка) → заказ в RAKETA (название без латиницы `raketa/raketa-title.ts`, китайское описание = engine `titleRaw`, продавец Poizon id 5, декларант — владелец). Можно прислать **RA-номер** — привяжет существующий. Дубли по треку не создаются. **Несколько вещей одним треком** (Poizon так иногда шлёт): тот же китайский трек у другой вещи заказа → вещь добавляется в существующий заказ RAKETA (`addOrderItem`, PUT с доп. товаром); в «только RAKETA» вещи группируются по треку. Объединение/оплата/трекинг считают **разные заказы RAKETA** (`distinctRaketaOrderIds`), не вещи.
  2. Когда все вещи зарегистрированы и у заказа есть ПВЗ → получатель + адрес СДЭК (переиспользуются существующие) → 1 вещь: на заказ (PUT), несколько: **объединение** (`raketa_title` или «LP042 Иванов N шт»).
  3. `orders.fulfillment_manual` — «оформить вручную», автоматика не трогает.
  4. **Оплата доставки** — `orders/services/raketa-delivery-payment.service.ts`, cron каждые 10 мин:
     - все вещи объединения «На складе в Китае» → сервер жмёт «Собрать» (`POST /close_consolidation/{id}`, с проверками сторожа — п. 6) и пишет клиенту «Посылка собирается»; RAKETA пакует 4–6 ч;
     - появилась цена (`GET /price/{consolidation|order}/{id}`, `controls.pay_button`) → клиенту сумма строк `price`+`services` (межд. доставка + по РФ + пошлина + страховка, без скидок) → ссылка пополнения баланса RAKETA (`POST /billing {amount:{value}}` → `returnUrl`), статус `DELIVERY_PAYMENT_PENDING`, `actualDeliveryRub/actualDutyRub` заполняются;
     - оплата ловится по **росту основного баланса** (`GET /auth/me/` → `balance_details.main`; пополнения картой в `billing_history` НЕ попадают): база в `raketa_state.balance_main`, рост = сумма открытой ссылки (или до 3 ссылок) → `DELIVERY_PAID` (+`dutyPaidAt`), затем `POST /pay/{id}/{kind}`; свои оплаты вычитаются из базы; суммы ссылок уникальны (+1 ₽); непонятное поступление → сообщение владельцу;
     - `/price/*` отдаёт суммы **в копейках** (клиент переводит в рубли); счёт > 50 000 ₽ клиенту не уходит. При оплате RAKETA сначала списывает бонусы, потом основной баланс;
     - объединения не из наших заказов (личные «только RAKETA»): тоже «Собрать» + сообщение владельцу с ценой (таблица `raketa_consolidations`). Заказ без клиента — только сообщение владельцу с ценой. Оплачено в кабинете вручную (`paid_button`) → заказ сам переходит в `DELIVERY_PAID`.
     - Клиент: кнопка «Оплатить доставку» в уведомлении и на странице заказа (`POST /orders/:id/delivery-payment-link`, ссылка обновляется через 6 ч).
  4б. **Адрес RAKETA** несёт перевозчика, тип (pvz/kd) и тариф — так RAKETA знает Почта/курьер/Экспресс: `findOrCreateAddress` ищет совпадение по tk+тип+тариф+ПВЗ (или индекс+улица+дом+кв.), иначе `POST /customer_address` (проверено вживую 2026-10-17: Почта ПВЗ Экспресс и курьер СДЭК создаются, повторный поиск находит).
  5. **Отслеживание** — `orders/services/raketa-tracking.service.ts`: публичный трекер RAKETA `GET https://my.raketacn.ru/api/get_statuses?track_number=` (без входа, события + 7 этапов, кэш 10 мин). Одиночный заказ — по RA… вещи; объединение — сначала каждая вещь до склада в Китае, потом посылка по RAC… (`orders.raketa_parcel_track`). Клиенту: `GET /orders/:id/tracking` → блок «Отслеживание посылки». Синк каждые 30 мин (:05/:35): сохраняет RAC… и трек СДЭК (`raketa_tk_track`), «В пути по РФ» → `TRACK_CODE_RECEIVED` с треком СДЭК, «Доставлен» → `DELIVERED` (клиенту уведомления). Трек СДЭК показывается клиенту сразу, как появится (обычно сразу после оплаты); номера RAKETA (RA…/RAC…) и слово «RAKETA» клиенту не показываются. Трек Почты — со ссылкой на pochta.ru (`carrierTracking` в shared, `tracking.carrier`); у пунктов партнёра трека нет — «В пути по РФ» переводит в `TRACK_CODE_RECEIVED` без трека.
  6. **Сторож** — `orders/services/raketa-guard.service.ts` (после аудита 2026-10-12, случай L046): общий per-order lock для всех операций RAKETA (регистрация, доставка, «Собрать», цена, оплата, клики в панели); `inspect()` сверяет заказ с кабинетом (трек вещи = трек её заказа RAKETA, заказ RAKETA не привязан к двум нашим заказам, кол-во вещей в заказе RAKETA = привязанным у нас, объединение одно и ровно из наших заказов). Вызывается перед «Собрать», отправкой цены клиенту, оплатой и раз в 30 мин (:15/:45). Расхождение → **карантин**: `fulfillment_manual = true`, причина в `raketa_last_error`, сообщение владельцу; включить автоматику обратно можно только когда сверка чистая. «Собрать» для объединения с нашими заказами — только если оно одно, привязано к своему заказу, всё зарегистрировано и 30 мин без изменений. Регистрация: найденный заказ RAKETA привязывается, только если он ничей и трек совпадает; новые вещи после оформления доставки — только вручную; перед созданием объединения проверяется, что заказы не лежат в другом; после — что в нём ровно наши. `addOrderItem` идемпотентен и перепроверяет результат. Скрытые заказы (`hidden_from_client`) — без ссылок клиенту и без трекинг-уведомлений.
