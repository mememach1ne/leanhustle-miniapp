# MVP «Магазин» (витрина) — план

## 0. Контекст
Добавляем в miniapp витрину популярных товаров Poizon. Источник данных — **движок цен** (`lh-dewu-engine`, `http://127.0.0.1:3777`, заголовок `x-api-token`), тот же, что уже питает резолв товара (`DewuApiClientService`). Деталь товара по `spuId` уже работает и возвращает `DewuResolvedProduct` (цены по размерам, размерная сетка, фото).

Движковую часть (`GET /catalog`) делает отдельная сессия проекта **dewu-api**. Эта задача — про miniapp: БД, API, UI. Кодить можно под контракт ниже.

## 1. Контракт движка (dewu-api сессия готовит этот endpoint)
```
GET http://127.0.0.1:3777/catalog?page=<n>
Header: x-api-token: <DEWU_ENGINE_TOKEN>
```
Ответ:
```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "pageNum": 1, "pageSize": 60, "total": 1240, "pages": 21,
    "items": [
      {
        "spuId": "2354",
        "title": "Nike Air Force 1 Low '07 White",
        "article": "315122-111",
        "image": "https://cdn.poizon.com/pro-img/....jpg",
        "priceCny": 669.00,
        "priceFen": 66900,
        "soldText": "64w+"
      }
    ]
  }
}
```
- `priceCny` — цена «от» (минимальный бид), для превью. Точные цены по размерам берутся при открытии карточки через существующий резолв.
- `spuId` из каталога **совпадает** с id детали (проверено): его можно слать в резолв напрямую.
- **Готово и живёт сейчас:** endpoint `GET /catalog?page=` уже поднят на движке.
- **MVP-ограничение (важно):** надёжно отдаётся только **страница 1 = 60 самых популярных** товаров (быстро, кэш 30 мин). `page=2+` пока возвращает пустой `items`: в headless сетка `/home` не рисуется → пагинацию/категории дёрнуть нечем, а тело запроса зашифровано. Поэтому **синк должен останавливаться на первой пустой `items`**. Расширение до сотен товаров — через шаг «категории» (§7).
- Позже: `&category=<code>` и отдельный `GET /search?q=`.

## 2. Модель данных (Prisma) — `CatalogProduct`
- `spuId` String @id
- `title` String
- `article` String?
- `imageUrl` String
- `priceCny` Decimal
- `priceRub` Decimal        // посчитать при синке через существующий FX (CBR × markup)
- `soldText` String?        // "64w+"
- `soldRank` Int @default(0) // распарсить "64w+" → 640000 для сортировки
- `popularityOrder` Int      // позиция в ленте (стабильная сортировка)
- `category` String?         // на будущее
- `isActive` Boolean @default(true)
- `lastSyncedAt` DateTime
- индексы: `@@index([isActive, popularityOrder])`, `@@index([soldRank])`

## 3. Синхронизация каталога (apps/api) — `CatalogSyncService`
- Тянет из движка `GET /catalog?page=1..K` последовательно (пауза ~1с). **Сейчас реально приходит только страница 1 (60 товаров)** — цикл останавливается на первой пустой `items`. Когда добавим категории, K вырастет и товаров станет сотни.
- `upsert` в `CatalogProduct`: `priceCny`→`priceRub` через **существующий FX-сервис**, `soldText`→`soldRank`, `popularityOrder` (глобальный счётчик по мере обхода), `lastSyncedAt`, `isActive=true`.
- Не встреченные в проходе → `isActive=false` (не удалять).
- Запуск: по расписанию (`@Cron`, ежедневно ночью) + ручной триггер `POST /api/admin/catalog/sync` (админ-гвард).
- **Важно:** пользовательские запросы витрины движок НЕ дёргают — только этот джоб. Витрина читает из БД.

## 4. API витрины (apps/api)
- `GET /api/catalog?page=&limit=&sort=popular` — читает из `CatalogProduct` (`isActive=true`, сорт по `popularityOrder`/`soldRank`), пагинация. Отдаёт карточки (id, title, image, priceRub, priceCny, soldText).
- Открытие карточки: переиспользовать резолв по `spuId`. **Нюанс:** сейчас `ProductsService.resolveProduct` принимает `{ link }` и гоняет через `DewuLinkResolverService`. Для витрины добавить путь резолва **по готовому `spuId`** (пропустить link-resolver; rate-limit для просмотра из каталога можно ослабить — это наш кураторский трафик). Маппер, кэш, `DewuResolvedProduct` — как есть.
- (Позже) `GET /api/catalog/:spuId/similar` — тот же бренд/категория/ценовой диапазон из БД.

## 5. Фронт (apps/web, Next.js)
- Новая вкладка/маршрут **«Магазин»**.
- Сетка карточек: фото, название (обрезка), цена **«от ₽…»** (опц. + «¥…»), бейдж «продано: 64w+», порядок по популярности.
- Бесконечный скролл/пагинация через `GET /api/catalog`.
- Тап по карточке → **существующий экран карточки** по `spuId` (размеры/цены/сетка + текущий флоу «в корзину/заказ»). Переиспользовать имеющиеся компоненты.

## 6. Консистентность цен (решить)
В детали цена размера = `GLOBAL + ¥2`, затем ×FX. Цена «от» в каталоге — минимальный бид (¥669). Рекомендация: показывать «от» **по той же формуле** (`+¥2`, тот же FX), чтобы число совпадало с карточкой. (Если хочется «честное от» без +¥2 — ок, но зафиксировать единообразно.)

## 7. Вне MVP (следующие шаги)
Категории (`&category=`), поиск (`/search`), алерты о снижении цены, избранное, персонализация «для вас» (на заказах/лояльности).

## 8. Конфиг
Переиспользовать `DEWU_ENGINE_URL` / `DEWU_ENGINE_TOKEN` (как в `DewuApiClientService`) для вызовов `/catalog` из `CatalogSyncService`.

---
Связка сторон: пока dewu-api сессия делает `GET /catalog`, здесь можно готовить БД/миграцию, `CatalogSyncService` (под контракт), API и UI. Полный сквозной тест — когда endpoint движка поднят.

# Фильтры и поиск (v2 — движковый endpoint УЖЕ готов и живёт)

**Идея:** фильтры = поисковые запросы. У поиска портала keyword в URL (`/search?keyword=...`), поэтому headless тянет любой запрос.

**РЕШЕНО (работает): `/search?q=` отдаёт настоящий портальный «Best Sellers» + цены.** Движок открывает страницу поиска в stealth-браузере (обходит анти-бот-рендер), кликает таб «Best Sellers» и снимает результат. Проверено: `nike` → AF1 259w+, Air Monarch 236w+, Dunk 183w+ (как на сайте), с ценами. Работают любые запросы — бренд, тип, бренд+тип, свободный текст.

## Контракт движка (готов)
```
GET http://127.0.0.1:3777/search?q=<keyword>   (header x-api-token)
→ { code, msg, data: { query, pageNum, pageSize, total, pages,
     items: [{ spuId, title, article, image, priceCny, priceFen, soldText, soldRank }] } }
```
- 60 результатов (страница 1), сортировка **настоящий Best Sellers** портала (`data.sortedByBest:true`), кэш 30 мин на запрос.
- **`priceCny`/`priceFen` заполнены** (цена «от», ¥ и фэни) — можно показывать прямо в гриде фильтров. Точная цена по размерам — как обычно, при открытии карточки.

## Фильтры (UI в miniapp — склеивают keyword, english) — РЕШЕНО (2026-09-16, финальная структура)
**Бренд-чипы убраны** (брендов слишком много для чипов). Вместо этого:
1. **Фильтр «Категория/тип вещи»** — чипы: Sneakers, Jacket, Hoodie, T-Shirt, Pants, Shorts, Bag, Backpack, Cap, Slides, Accessories. **НЕ через реальные вкладки категорий портала** — их всего ~6-7 (Shoes/Apparel/Bags/Women's Apparel/Accessories/Kids' Shoes), слишком грубо для фильтра типа. Вместо этого — курируемый keyword как раньше.
2. **Фильтр сортировки** (переключатель/табы): Best Sellers / Дёшево→Дорого / Дорого→Дёшево (`sort=best|price_asc|price_desc`).
3. **Строка поиска** (сверху/рядом) — свободный текст, в первую очередь для бренда, но подходит для любого запроса.

**Проверено (2026-09-16): поиск «только бренд» теперь ЧИСТЫЙ.** Раньше (до реального Best Sellers) `adidas` без типа выдавал шум (парфюм/гели). Со свежим (без гонки) вызовом `sort=best` — идеально чистый монотонный список: Superstar 190w+/¥518, Samba OG 177w+/¥405, Superstar Low 137w+/¥339... Значит **бренд можно вводить и без выбора типа** — не обязательно комбинировать.

- keyword = `"<type>"` (категория без бренда) / `"<brand>"` (поиск без категории) / `"<brand> <type>"` (оба выбраны) / произвольный текст.
- Комбинация бренд+тип (`"nike jacket"`, `"adidas jacket"`) — тоже проверено, чисто.
- Тип без бренда (`"jacket"`) — тоже проверено, чисто (CAMEL, Adidas и др. вперемешку по продажам).

## Ограничения (уже некритичные)
- **60 результатов на запрос** (страница 1). Пагинация возможна тем же stealth-способом (скролл), но пока не сделана — для фильтров 60 бест-селлеров достаточно.
- Запрос uncached идёт ~10–20с (stealth рендерит страницу + клик), поэтому **кэш обязателен** (в движке 30 мин + в БД miniapp). На пользователя движок дёргаем только при промахе кэша.
- Сортировки Price↑/↓/New тоже доступны (клик по соответствующему табу) — если понадобятся, добавим в движок параметром.

## Рекомендованная структура витрины
- Вкладка **«Популярное»** (по умолчанию) = `GET /catalog` — бест-селлеры с ценами.
- Панель **«Фильтры/Поиск»** = `GET /search?q=` — тип/бренд/строка; **в гриде есть цена «от»** + бейдж продаж; точная цена по размерам — в карточке.

## Миниапп-сторона
- `GET /api/catalog/search?brand=&type=&q=` → склеивает keyword → зовёт движок `/search` → кэширует по keyword (БД, TTL ~30–60 мин) → карточки.
- Чипы тип/бренд + строка поиска. Карточка: фото, название, **цена «от» (₽ из priceCny×FX)**, бейдж продаж; точная цена по размерам — на экране товара.

# Кэш-стратегия: суточный снапшот (принято)

Цель: **не дёргать движок/портал на каждый показ.** Раз в сутки собираем топ-карточки → витрина/фильтры/поиск живут из БД. Портал трогаем только (1) в ночном снапшоте и (2) когда человек открывает товар/корзину — там сверяем реальную цену.

- **Ночной джоб (`@Cron`, 1×/сутки) `CatalogSyncService`:**
  - `GET /catalog?page=1` → «Популярное» (бест-селлеры с ценами).
  - Для каждого keyword из курируемого списка (бренды, типы, топ «бренд+тип») → `GET /search?q=<kw>` (Best Sellers + цены). Дедуп по `spuId`; сохраняем `keyword/category`-тег, `priceRub = priceCny×FX`, `soldRank`, `snapshotAt`.
  - Итого ~N вызовов движка в сутки (N = размер списка), **последовательно, с паузой ~1–2с**. Портал почти не трогаем.
- **Витрина / фильтры / поиск — 100% из БД** (`CatalogProduct`). Быстро, без риска бана, устойчиво: если движок/сессия временно недоступны — витрина показывает вчерашний снапшот.
- **Реальная цена — только при открытии товара/корзины:** существующий резолв `/raw/:spuId` (живые цены по размерам). Заодно можно освежить `CatalogProduct.priceCny/priceRub` из свежей детали.

Замечания:
- «Все карточки» = **топ бест-селлеров по каждой категории/keyword** (не все 5М). 60/запрос × ~40–60 keyword'ов ≈ 2.5–3.5к уникальных карточек.
- Курируемый список keyword'ов = таксономия фильтров (бренды × типы). Держать в конфиге/БД, чтобы менять без кода.
- Поиск на витрине по умолчанию — по снапшоту в БД (тег/подстрока в названии). Для свободных запросов вне снапшота — опционально живой `/search` с записью в кэш.
- Модель `CatalogProduct` из §2 дополнить: `keywords String[]` (какими запросами пришёл), `snapshotAt DateTime`.

**Нужно от движка (если хотим глубже 60/категория):** сейчас 60 на запрос хватает. Если понадобится 200–300 на категорию или настоящие портальные категории — движок это умеет (stealth: скролл-пагинация + клик по табам категорий); добавлю `GET /search?q=&pages=N` и/или `GET /category/:code`.

# Поиск + сортировка по цене (v3 — движок ГОТОВ, замерено)

## Контракт движка (готов и живёт)
```
GET http://127.0.0.1:3777/search?q=<keyword>&sort=<sortKey>   (header x-api-token)
  sortKey ∈ { best, price_asc, price_desc, featured, new }, default best
→ { code, msg, data: { query, sort, pageNum, pageSize, total, pages,
     items:[{spuId,title,article,image,priceCny,priceFen,soldText,soldRank}] } }

GET http://127.0.0.1:3777/search/multi?q=<keyword>&sorts=best,price_asc   (comma-list)
→ { code, msg, data: { best:{...}, price_asc:{...} } }   -- ОДИН заход на страницу для всех сортировок сразу
```
- Реальный клик по табу портала (Best Sellers / Low to High / High to Low / New Arrivals) через stealth-браузер — не client-side ре-ранк, настоящая сортировка сайта. Рендер триггерит и ленивую загрузку цены → в гриде есть `priceCny`.
- **Замеренная стоимость:** один заход + 1 сортировка ≈ **11–16с** (холодно); **+1 доп. сортировка на том же заходе** (`/search/multi`) ≈ **+4–5с**, а не полный повторный заход (~12-15с). Поэтому для двух сортировок разом `/search/multi?sorts=best,price_asc` дешевле и безопаснее (меньше навигаций = меньше следов), чем два раздельных вызова `/search`.
- Кэш 30 мин **на пару (keyword, sort)** — повторный вызов ≈ 10мс.

## ⚠️ Важный нюанс качества данных: `price_asc`/`price_desc`
На сортировке «Low to High» у части товаров `priceCny: null` — это **не баг**, а как ведёт себя сам портал: товары без активной цены/наличия сортируются как «0», поэтому вылезают в начало списка «по возрастанию». **На стороне miniapp обязательно фильтровать** `priceCny != null && priceCny > 0` перед показом сортировки по цене (иначе пользователь увидит пустые карточки без цены сверху).

## Итог по стоимости для ночного снапшота
Одна связка `/search/multi?sorts=best,price_asc` на keyword ≈ **11–16с**. При списке ~40–60 keyword'ов (бренды×типы) — это **~10–16 минут суммарно, один раз в сутки**, последовательно с паузой 1–2с между keyword'ами. Совсем не затратно: один проход по прокси-IP ночью, витрина весь день читает БД.

## Что это даёт продукту
- **Поиск:** свободный текст/тип/бренд работает через `/search?q=` — приемлемо, минимальный поиск реализуем.
- **Сортировка по цене:** «от дешёвых» и «от дорогих» — реальные, с портала, не имитация.
- **Best Sellers:** уже был готов раньше (см. §2 выше) — тоже настоящий, не ре-ранк.

## Что делать в miniapp (обновление §«Миниапп-сторона» и «Ночной джоб»)
- Ночной `CatalogSyncService`: на каждый keyword вызывать `GET /search/multi?q=<kw>&sorts=best,price_asc` (не два отдельных `/search`). Сохранять оба среза в `CatalogProduct` (можно как два признака сортировки/ранга на товар, либо отдельные материализованные списки `bestOrder`/`priceAscOrder` по keyword).
- Отдавать в UI переключатель сортировки «Популярное / Сначала дешёвые» — оба читаются из БД (снапшота), без обращения к движку на пользовательский показ.
- Фильтр `priceCny > 0` применять **при синке** (не хранить в БД товары без цены для price_asc-среза) — тогда фронту вообще не нужно ничего фильтровать в рантайме.
- Живой поиск вне снапшота (см. «Кэш-стратегия») — по умолчанию `sort=best`; можно добавить переключатель сортировки и туда через `sort=price_asc` (тот же движок, тот же кэш).
